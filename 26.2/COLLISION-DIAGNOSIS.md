# Диагностика столкновений самолётов (26.2)

Все выводы сверены с реальными исходниками движка в `/opt/mc-src` (Minecraft 26.2,
деобфусцированный, 7055 `.java`). Ссылки вида `файл:строка` на мод — по состоянию
**до правки** (`git show HEAD:...`).

---

## TL;DR — почему «9 из 10 не детектится»

Детекта горизонтального столкновения **не существует вообще**: выражение, которое решает,
крашить самолёт или нет, на 26.2 тождественно равно `-5.0` и сравнивается с `5.0`.
Вертикального детекта тоже нет: единственный путь (`causeFallDamage`) срабатывает только
при крене > 45°. Те «1 из 10», что пользователь всё-таки видит — это как раз касание земли
с креном > 45°, и там срабатывание бинарное (мгновенный взрыв независимо от скорости).

## Гипотеза 1 — порог `f2 > 5.0F` недостижим. **ПОДТВЕРЖДЕНА**

`PlaneEntity.java:562-580` (оригинал):

```java
double speedBefore = Math.sqrt(getDeltaMovement().horizontalDistanceSqr());
...
move(MoverType.SELF, motion);
...
double speedAfter = Math.sqrt(getDeltaMovement().horizontalDistanceSqr());
double speedDiff  = speedBefore - speedAfter;
float  f2 = (float) (speedDiff * 10.0D - 5.0D);
if (f2 > 5.0F) { crash(f2); }
```

`f2 > 5` ⟺ **`speedDiff > 1.0 блока/тик = 20 блоков/с**.

### Реальная максимальная скорость (посчитано, не угадано)

Константы мода: `push = 0.00625 * throttle` (`PlaneEntity.java:530`),
`maxPushSpeed = getMaxSpeed() * 10` (`:671`), `MAX_SPEED` всегда `1f`
(ставится в конструкторе `PlaneEntity:133`, нигде больше не переопределяется →
`maxPushSpeed = 10`), тяга гасится как
`push * clamp(1 - dot*speed/(maxPushSpeed*(push+0.05)), 0, 2)` (`:809`),
сопротивление `0.001·v² + 0.0005·v + 0.001` (`:1431-1433`), `maxSpeed = 3` (`:1426`).

Численное решение равновесия `тяга = сопротивление`:

| throttle | push | терминальная скорость |
|---|---|---|
| 1 | 0.00625 | 0.437 б/т = 8.7 б/с |
| 3 | 0.01875 | 0.627 б/т = 12.5 б/с |
| **5 (максимум без бустера)** | **0.03125** | **0.763 б/т = 15.3 б/с** |
| 10 (с `BoosterUpgrade`) | 0.0625 | 1.079 б/т = 21.6 б/с |

**`speedBefore ≤ 0.763`** в обычном полёте, а нужно `speedDiff > 1.0`. Даже лобовой удар
на полном газу с полной остановкой даёт `f2 = 0.763*10 - 5 = 2.6` — вдвое ниже порога.
Порог достижим только в затяжном пикировании на бустере.

> Побочно: в 1.21.1 `speedBefore` считался как `Math.sqrt(MathUtil.getHorizontalDistanceSqr(...))`,
> а `getHorizontalDistanceSqr` на самом деле возвращает **не** квадрат, а `sqrt(x²+z²)`
> (`1.21.1/.../MathUtil.java:9-11`). То есть там был `sqrt(sqrt(v))`. Точка срабатывания
> та же (`sqrt(v) > 1 ⟺ v > 1`), так что порт этого не сломал — баг унаследован.

## Гипотеза 8 — клиент/сервер. **ПОДТВЕРЖДЕНА, ЭТО КОРНЕВАЯ ПРИЧИНА №1**

Это не догадка, а прямое следствие трёх мест в `/opt/mc-src`.

### 8.1 Кто авторитетен

`Entity.java:3568-3579`:

```java
public final boolean isLocalInstanceAuthoritative() {
    return this.level.isClientSide() ? this.isLocalClientAuthoritative() : !this.isClientAuthoritative();
}
public boolean isClientAuthoritative() {
    LivingEntity passenger = this.getControllingPassenger();
    return passenger != null && passenger.isClientAuthoritative();
}
public boolean canSimulateMovement() { return this.isLocalInstanceAuthoritative(); }
```

`Player.java:1254-1257`:

```java
@Override
public boolean isClientAuthoritative() { return true; }   // безусловно
```

⇒ **на сервере**, пока самолётом управляет игрок,
`isClientAuthoritative() == true` ⇒ `isLocalInstanceAuthoritative() == false` ⇒
`canSimulateMovement() == false`.

### 8.2 Что это ломает внутри `move()`

`Entity.java:718-805`:

```java
boolean xCollision = !Mth.equal(delta.x, movement.x);      // эпсилон 1.0E-5 (Mth.java:162)
boolean zCollision = !Mth.equal(delta.z, movement.z);
this.horizontalCollision = xCollision || zCollision;       // ← это работает всегда
...
if (this.isLocalInstanceAuthoritative()) {
    this.checkFallDamage(movement.y, this.onGround(), effectState, effectPos);   // ← НЕ вызывается
}
...
if (this.canSimulateMovement() && (movedVertically && this.verticalCollision || this.horizontalCollision)) {
    this.restituteMovementAfterCollisions(effectState, xCollision, zCollision, movement);  // ← НЕ вызывается
}
```

`restituteMovementAfterCollisions` (`Entity.java:803-845`) — это **единственное** место, где
после столкновения обнуляются заблокированные оси `deltaMovement`
(`restitution = 0` ⇒ `-currentMovement.x * 0 = 0`).

Поскольку на сервере оно пропускается, между `speedBefore` и `speedAfter` вектор скорости
**не меняется вообще**. Единственное, что ещё трогает дельту в `move()` — это
`getBlockSpeedFactor()` (`Entity.java:1090`), который для подавляющего большинства блоков равен `1.0`.

> **Итог арифметики: `speedAfter == speedBefore` ⇒ `speedDiff == 0` ⇒ `f2 == -5.0` ⇒
> `crash()` из горизонтальной ветки не может сработать НИКОГДА.**
> Не «редко», не «при малой скорости» — тождественно никогда, пока в самолёте сидит игрок.

Это **регрессия 26.2**: `isClientAuthoritative` / `canSimulateMovement` — новый API
(client-authoritative players), в 1.21.1 обнуление дельты в `move()` было безусловным.
Там `speedDiff` был честным, просто не дотягивал до порога (гипотеза 1).

### 8.3 Двигается ли самолёт на сервере своей физикой?

И да, и нет — и это важно для выбора места детекта.

`ServerGamePacketListenerImpl.handleMoveVehicle` (`:443-520`):

```java
vehicle.move(MoverType.PLAYER, new Vec3(xDist, yDist, zDist));   // проверка коллизий клиентского шага
...
vehicle.absSnapTo(targetX, targetY, targetZ, targetYRot, targetXRot);   // ТЕЛЕПОРТ в клиентскую позицию
Vec3 clientDeltaMovement = new Vec3(vehicle.getX() - oldX, vehicle.getY() - oldY, vehicle.getZ() - oldZ);
this.handlePlayerKnownMovement(clientDeltaMovement);              // → player.setKnownMovement(...)
vehicle.setOnGroundWithMovement(packet.onGround(), clientDeltaMovement);
vehicle.doCheckFallDamage(clientDeltaMovement.x, clientDeltaMovement.y, clientDeltaMovement.z, packet.onGround());
```

То есть **позиция на сервере приходит от клиента**, а мод при этом продолжает крутить
полную физику и на сервере тоже. Для сравнения, ванильная лодка так не делает
(`AbstractBoat.java:229-243`): `move(MoverType.SELF, ...)` вызывается **только**
при `isLocalInstanceAuthoritative()`, иначе `setDeltaMovement(Vec3.ZERO)`.

Практические следствия:

* Серверный `move(SELF, ...)` мода — это «теневая» симуляция из клиентской позиции.
  Её **геометрия достоверна** (самолёт стоит там же, где у клиента, значит `collide()`
  реально упирается в ту же стену) — `horizontalCollision` на сервере честный.
* Её **скорость недостоверна**: из-за 8.2 серверная дельта после удара не обнуляется,
  сервер «продолжает лететь в стену» на крейсерской скорости бесконечно.
* Зато `Entity.getKnownMovement()` (`Entity.java:3997`) на сервере отдаёт
  `ServerPlayer.lastKnownClientMovement` (`ServerPlayer.java:2167-2169`), который
  `handleMoveVehicle` заполняет **реальным смещением самолёта за тик**. Это единственное
  авторитетное измерение скорости, доступное серверу.

Проверено дополнительно: когда игрок — пассажир, `handleMovePlayer`
(`ServerGamePacketListenerImpl.java`, ветка `if (this.player.isPassenger())`) только
поворачивает игрока и `knownMovement` не трогает, так что значение не затирается.

## Гипотеза 3 — вертикальные столкновения не обрабатываются. **ПОДТВЕРЖДЕНА**

`horizontalCollision` — единственный проверяемый флаг (`PlaneEntity.java:570`).
`verticalCollision` / `verticalCollisionBelow` (`Entity.java:236-237`) не читаются нигде.

Единственный «вертикальный» путь:

```java
// PlaneEntity.java:1071-1079
protected void checkFallDamage(double y, boolean onGroundIn, BlockState state, BlockPos pos) {
    if ((onGroundIn || isOnWater())) {
        final double y1 = transformPos(new Vector3f(0, 1, 0)).y();
        if (y1 < Math.cos(Math.toRadians(getLandingAngle()))) {   // наклон > 30°
            state.getBlock().fallOn(level(), state, pos, this, getDeltaMovement().length() * 5);
        }
        fallDistance = 0.0F;
    }
}
// PlaneEntity.java:1086-1091
public boolean causeFallDamage(double fallDistance, float damageMultiplier, DamageSource src) {
    if (degreesDifferenceAbs(rotationRoll, 0) > 45) { crash((float)(fallDistance * damageMultiplier)); }
    return false;
}
```

Два независимых дефекта:

1. **Пикирование в землю с ровными крыльями (roll ≈ 0) не наносит ничего.** Это самый
   типичный «влетел в гору» — и он полностью бесплатен.
2. **Касание земли с креном > 45° — мгновенный взрыв при ЛЮБОЙ скорости.** `crash()`
   игнорирует свой аргумент (см. гипотезу 4b). Задел крылом на 1 блок/с на посадке = смерть.
   Это и есть «1 из 10, которое детектится».

Дополнительно: `checkFallDamage` вызывается из `Entity.move()` **только** при
`isLocalInstanceAuthoritative()` (`Entity.java:784-786`), т.е. на сервере под игроком —
не вызывается. Он доходит до сервера единственным путём — через
`handleMoveVehicle → doCheckFallDamage` (`Entity.java:1546-1553`). То есть путь жив,
но узкий, и завязан на пакеты клиента.

## Гипотеза 2 — гейт `onGroundTicks <= 0`. **ПОДТВЕРЖДЕНА (вторичная)**

`PlaneEntity.java:835-839`:

```java
if (onGroundTicks < 0) { onGroundTicks = 5; } else { onGroundTicks--; }
```

Пока самолёт на земле, счётчик циклится `5,4,3,2,1,0,-1 → 5,...`, то есть
**5 тиков из 7 детект заглушен**. `tickOnGround` вызывается при
`getOnGround() || isOnWater()` (`:538`), а `isOnWater()` (`:1112-1115`) смотрит блок на
`y + 0.4` — значит **низкий полёт над водой постоянно перевзводит счётчик в 5** и глушит
детект столкновений у берега. В воздухе счётчик уходит в минус за ≤6 тиков, так что для
чистого полёта это не главная причина.

## Гипотеза 4 — `setOnGround(true)` перед `move()`. **ОПРОВЕРГНУТА (как причина)**

`PlaneEntity.java:565-567`. По коду движка:

* `Entity.collide()` (`Entity.java:1144-1152`) использует `this.onGround()` только для
  step-up, и то под условием `this.maxUpStep() > 0.0F`. `Entity.maxUpStep()`
  (`Entity.java:3901`) возвращает `0.0F`, `PlaneEntity` его не переопределяет ⇒ ветка мертва.
* Флаги коллизий выставляются **после** `collide()` из сравнения запрошенного и фактического
  вектора и от `onGround()` не зависят.
* `setOnGroundWithMovement(verticalCollisionBelow, this.horizontalCollision, movement)`
  (`Entity.java:773`) перезаписывает `onGround` результатом `move()`, так что хак
  «живёт» ровно до конца `collide()`.

Единственный реальный эффект — лишние вызовы `checkSupportingBlock` (`Entity.java:690`).
На детект не влияет.

Заодно: `minorHorizontalCollision` (`Entity.java:238`) для самолёта всегда `false`,
т.к. `isHorizontalCollisionMinor` (`Entity.java:1015`) в базовом `Entity` возвращает `false`,
а `PlaneEntity` не переопределяет. Новых флагов, которые мод бы игнорировал, нет.

## Как теперь измеряется удар

* **Предикат** — геометрия серверного `move(SELF, ...)`, поосно: ось считается заблокированной,
  когда `|wanted_ось − achieved_ось| > 1e-5`, где `achieved = позиция после − позиция до`.
  Позиции, а не `deltaMovement`, — потому что `deltaMovement` на сервере как раз и не
  обрабатывается движком (причина №1). Любой урон требует этого **позитивного геометрического
  свидетельства контакта**; из одной лишь истории скоростей не выводится ничего (см. раздел
  «Две регрессии первой версии» ниже — почему).
* **Величина** — `vHit`: **полная** компонента `wanted` на заблокированных осях,
  `impact = |vHit|`. На тике первого касания это настоящая скорость сближения — где именно
  внутри тика оказалось препятствие, не важно. Сразу после удара движок (или
  `restoreCollisionResponse`) обнуляет заблокированные оси, поэтому следующие тики несут только
  то, что физика успела восстановить (тяга ≈0.03, гравитация ≈0.05–0.08 б/т): стоянка у стены
  и лежание на земле ниже любого допуска.
* **Классификация** — по направлению `vHit`: доля снижения > 0.7 ⇒ вертикальный удар
  (посадочный допуск с бонусом за ровные крылья), иначе горизонтальный (стена/склон).
* `getKnownMovement()` в расчёте урона о блоки **не участвует вообще**. Он остался только как
  оценка скорости для чиркания крылом и таранов, и там всегда берётся
  `min(двух соседних сэмплов)` — одиночный пакетный сбой (нулевой сэмпл или сдвоенный
  «догоняющий») не может ни завысить, ни включить урон.
* Дополнительно восстановлена пропущенная движком реакция на столкновение
  (`restoreCollisionResponse`): заблокированные оси `deltaMovement` обнуляются вручную,
  но **только** при `!canSimulateMovement()`, то есть строго там, где 26.2 это пропускает.
  Это чинит и саму рассинхронизацию (сервер переставал «лететь в стену вечно»).

# Две регрессии первой версии `PlaneCollisions` (найдены и исправлены)

Первая версия этого класса закрыла причины №1–№4, но пользователи продолжали видеть оба
симптома: «взрывается сам по себе в воздухе» и «не взрывается о стену». Оба воспроизведены
на стенде (`/autopilot` + логирование всех величин на каждом тике контакта) и объяснены.

## Р1 — величина удара мерилась как обрезок тика ⇒ лотерея фаз («не взрывается»)

Было: `blockedSpeed = |wanted| − |achieved|` — сколько движения мир «съел» **внутри этого
тика**. Но препятствие попадает в произвольную точку пути тика: если стена в конце пути,
самолёт успевает пролететь почти всё, и от удара на 3.0 б/т остаётся огрызок 0.1–0.5.
Настоящая уничтоженная скорость — вся компонента `wanted` по заблокированной оси (сразу после
этого её обнуляет реституция), а не остаток тика. Замеры стенда, один и тот же манёвр:

| сценарий | скорость | старый замер | урон | итог |
|---|---|---|---|---|
| пикирование в грунт (#67) | 1.67 б/т | 0.054 | 0.0 | **цел** |
| то же пикирование (#98) | 1.80 б/т | 1.438 | 24.4 | взрыв |
| лоб в стену на атакующей (#106) | 2.99 б/т | 0.555 | 5.7 | **цел, повис на стене** |

После правки (та же стена, тот же тик подлёта): `vHit = 2.476` ⇒ урон **122** ⇒ самолёт
уничтожен об стену. Пикирования 1.55–1.78 б/т дают 30–38 ⇒ уничтожен. Штатные касания:
стоянка/руление — контакт виден (`impact ≈ 0.087` за 4 тика гравитации), урон 0; шлепок с
2 блоков — 0.32 < допуска 0.55, урон 0; падение с 10 блоков — 0.51 ⇒ 0.8 (дробное, в
аккумулятор).

## Р2 — запасной путь по `knownMovement` ⇒ взрывы в чистом воздухе («взрывается сам»)

Был запасной детект: «авторитетная горизонтальная скорость упала за тик больше чем на
0.35 б/т — засчитать удар». Его кормил `getKnownMovement()`, а для самолёта под игроком это
**попакетное** смещение клиента, и движок сам делает его рваным:

* `ServerGamePacketListenerImpl.handleClientTickEnd` — если за клиентский тик не пришло
  пакета движения, `knownMovement` **обнуляется** (`setKnownMovement(Vec3.ZERO)`);
* опоздавший пакет несёт смещение **за два тика**, т.е. двойную скорость.

На крейсере 0.76 б/т один запоздавший/слитый пакет даёт последовательность сэмплов
`0.76 → 0 → 1.5`: «падение» на 0.76 > 0.35 ⇒ урон `20·(0.76² − 0.15²) ≈ 11.1` ⇒ мгновенное
уничтожение в чистом небе. Никакой контакт не требовался — это и был спонтанный взрыв.

Проверено на стенде, что собственной физике запасной путь не нужен: за все полёты (включая
пикирование 80° на 3 б/т и сваливание) `hLost` ни разу не превысил 0.2 **вне** тиков
реального контакта, а на тиках контакта работает основной, геометрический детект. Запасной
путь удалён целиком; оставшиеся потребители `knownMovement` (чиркание, тараны) берут
`min(двух соседних сэмплов)` — см. выше.

# Р3 — вода не считалась столкновением вообще («на огромной скорости ничего не делает»)

Жалоба: *«если самолет с воздушной подушкой — то при столкновении с водой на огромной
скорости ничего не делает»*. Воздушная подушка (`FloatingUpgrade`, Floaty Bedding) названа
виновником, но она лишь **вторая половина** проблемы.

## Половина 1 — у воды нет коллизии, поэтому её не видел детектор

Весь механизм выше опирается на ось, по которой `Entity.move()` **отказался** двигать
самолёт: `wanted − achieved > CONTACT_EPSILON`. У воды `getCollisionShape` пуст, `move()`
проходит сквозь неё насквозь, `horizontalCollision` остаётся `false`, ни одна ось не
блокируется. Ни один заряд урона не срабатывал. Вход в море на 3 б/т был бесплатным
**и с апгрейдом, и без него** — это проверено на стенде, обе машины уцелели.

## Половина 2 — апгрейд стирал снижение целиком

`FloatingUpgrade.tick()` делал `y = Mth.lerp(1, motion.y, Math.max(motion.y, 0))`, то есть
попросту `max(motion.y, 0)`: **каждый** тик над водой, при **любой** скорости, всё снижение
обнулялось. Пикирование на 3 б/т исчезало бесплатно, самолёт вставал на поверхности
невредимым. `tickUpgrades()` вызывается **до** `move()`, так что к моменту замера скорости
входа уже не существовало.

## Что сделано

**Правило входа в жидкость — отдельное, и оно тоже на положительном свидетельстве.**
Триггер — пересечённая за этот тик граница жидкости: блок в точке замера **не был** водой до
`move()` и **стал** водой после. Два реальных чтения блока, на тик друг от друга, границы,
которая никуда не движется. Никакой инференции по истории скорости —
`getKnownMovement()` здесь не читается вовсе, и это осознанно: именно догадка по падению
скорости давала прошлые ложные срабатывания на сетевых рывках (см. Р2).

Величина удара — `preUpgradeMotion`, скорость, которую оставила аэродинамика **до** того,
как `tickUpgrades()` успела её погасить. Точка замера — та же `y + 0.4`, что и в
`PlaneEntity.isOnWater()`, чтобы «апгрейд считает, что плывёт» и «детектор считает, что вошёл
в воду» не могли разойтись.

**Апгрейд гасит снижение с конечной скоростью, а не полностью.** `MAX_ARRESTED_DESCENT = 0.35`
б/т: поплавки — это плавучесть, а не аэрофинишёр. Мягкую посадку они гасят целиком, как и
раньше; пикирование уходит под воду.

| Константа | Значение | Смысл |
|---|---|---|
| `WATER_TOLERANCE_MIN` | 0.35 (7 б/с) | бесплатно при любом положении |
| `WATER_TOLERANCE_LEVEL_BONUS` | 0.35 | ровные крылья ⇒ порог 0.70 б/т = 14 б/с |
| `WATER_DAMAGE_FACTOR` | 10 | мягче земли (14/20) — вода мягче |
| `MAX_ARRESTED_DESCENT` | 0.35 | сколько снижения поплавки снимают за тик |

## Где проходит граница — измерено на стенде

Самолёт с Floaty Bedding, ровные крылья, вход строго вертикально у самой кромки воды,
здоровье 10 HP:

| скорость входа, б/т | здоровье после | урон |
|---|---|---|
| 0.60 | 10 | нет |
| 0.68 | 10 | нет |
| 0.75 | 9 | 1 |
| 0.85 | 8 | 2 |
| 1.00 | 5 | 5 |
| 1.20 | — | уничтожен |
| 1.50 | — | уничтожен |

**Граница бесплатной посадки на воду — 0.70 б/т (14 б/с)** при ровных крыльях; первый урон
около 0.75, разрушение с 1.2 (24 б/с). Без апгрейда вход на 1.5 б/т так же уничтожает
самолёт — дыра была не в апгрейде, а в детекторе. Уцелевшие машины остались плавать на
поверхности (`y ≈ −59.47` при кромке воды `−59`), то есть смысл апгрейда — работать с воды —
сохранён полностью.
